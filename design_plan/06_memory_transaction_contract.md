## 2. 地址与请求

### 2.1 RAM 和字节表示

- 使用 64 位无符号物理字节地址。
- 容量为配置中的字节数 N；有效字节范围为 `[0, N)`。
- 默认 N 为 `1,048,576 B`，即 1 MiB，不是十进制 1 MB。
- 全零初始化仅用于冷启动；恢复时装载保存的内存，不能再清零。
- 不含 MMIO、虚拟地址、多内存区域、原子读改写操作或缓存一致性。

Payload 是按地址递增排列的字节序列。写入地址 a 的 payload 第 i 字节对应 `memory[a+i]`。不把宿主整数表示直接视为线侧数据；将来若增加整数输入语法，需要另行明确端序。

### 2.2 访问合法性

长度 L 必须属于 `{1, 2, 4, 8, 16, 32, 64}`，且 `a mod L = 0`。写请求携带恰好 L 字节，覆盖本请求中的全部字节，无 byte-enable 掩码。读返回恰好 L 字节。

越界检查不能先做可能溢出的 `a + L` 再比较。语义要求是先确认 a 在范围内，再确认 `L <= N - a`。N 的可配置上限和宿主内存预算在 Q9 确定；不能因地址字段为 64 位就承诺可分配任意容量。

模型不自动把非法请求截断、回绕、拆分或拆成部分成功。合法小范围写可以覆盖更早大范围写中的一部分字节，这不等于支持 byte-enable。

### 2.3 请求身份

事务必须有可在所有源之间区分、可在 checkpoint 中恢复的稳定身份。C47 已确定 ID 不复用；编码可以是全局 ID，也可以包含源 ID 与局部序号。C57 选择 std::uint32_t/std::uint64_t 等固定宽度无符号类型，具体字段位宽及命名空间仍待冻结。C48 按事务自身责任终结及最后活动使用者结束回收记录；RAM 提交并不等于回收，独立转移后的 credit 责任也不必强留父事务，详见 [09](./09_discrete_event_kernel.md#47-id-不复用与按责任回收)。

源侧发出次序与目标接纳次序是不同数据。目标顺序身份必须在目标实际接纳时确定，不能使用宿主对象地址或线程执行偶然顺序生成。

## 3. 三个不同的完成时刻

```text
源接纳/发出
 -> 目标接纳
 -> 等待与服务
 -> 服务时序条件已满足
 -> 满足冲突顺序和资源条件后执行提交
 -> 响应保存/排队/传输
 -> 源接收并匹配响应，端到端完成
```

### 3.1 服务就绪与执行提交

Q2.1 所说的“目标服务完成时生效”，指目标**实际执行该次内存操作**的时刻；不把一个固定延迟计时器到期等同于必然已经执行。

Q4 已选择在服务启动前等待所有更早冲突请求执行提交。启动时不预留响应槽；计时到期但缺少响应保存空间时，仍保持未执行并占服务槽，读不取值、写不更新，直到可提交。详见 [08](./08_interconnect_and_memory_service.md#5-目标服务与响应背压)。

### 3.2 写入与读取

在执行提交点：

- 写请求一次性更新所覆盖的全部字节，并记录该写已执行。
- 读请求取得该点的全部请求字节，将它们固定为该读的响应 payload。
- 对其他内存操作而言，不观察该次操作执行一半的状态。

这是本模型的请求执行粒度，不是 ISA 原子指令，也不提供跨多个请求的原子性或持久化保证。Q4 已选择按字节计算多拍链路占用、完整消息交付，目标不因此提前执行部分写。

### 3.3 端到端完成

写响应表示相应写已经执行，但写可见不必等源端收到确认。读响应即使长期排队，也不能重新读取此后变化的内存。

内存提交、响应入接收队列、源消费匹配和 credit 返回互不等价；端到端完成指源消费匹配，不是 CDC 入队。服务槽在执行提交后释放，源消费释放响应接收槽；本地共享响应池槽保持至整条发送结束。不允许因为写已提交就删除仍待发送的确认责任；源 outstanding 的输入控制接口归 Q5。

## 4. 冲突与顺序

令请求 A 覆盖字节区间 `[a, a+L)`。在合法性检查之后，两个请求区间存在交集，且至少一个为写，才构成数据冲突：

| 较早请求 → 较晚请求 | 地址重叠时的执行约束 |
|---|---|
| 写 → 读（RAW） | 先更新内存，再为读固定数据 |
| 读 → 写（WAR） | 先为读固定数据，再允许写改变内存 |
| 写 → 写（WAW） | 较早写先执行，较晚写覆盖对应字节 |
| 读 → 读（RAR） | 无互相写入，不因彼此而阻塞 |

“较早”指同一内存目标实际接纳顺序。每个请求必须尊重所有更早、尚未执行的冲突请求；只检查紧邻前一个请求不够。

非冲突请求允许独立执行，不要求一定产生乱序。实际并行度、队列是否引入 HOL、仲裁和输出阻塞仍由资源模型决定。

Q4 请求侧采用消息 RR。C33 已确认同刻完成 CDC 的已授权消息全部登记，按该方向的发送序号分配目标接纳序号；该序号反映实际发送次序，不是“低源 ID 永远优先”。这些新入队请求不能同拍启动服务。

### 已执行不等于已响应

冲突依赖在前项执行提交后解除，不要求等前项响应回到源端。例如写已更新 RAM，但 ACK 仍堵在响应队列，此时后续冲突读可以在资源允许时读取新值。

### 不是源端程序序保证

同一源先发写、再发读，如果网络让读更早被目标接纳，读可能得到旧值。需要前后依赖的工作负载应显式等待写确认后再发读。

这条等待保证该写已经执行；若还有其他源后续写入，读可能看到更晚的值，不保证永远读到自己写的值。

## 5. 手工轨迹

以下时间只是教学假设，不是冻结的服务延迟或执行宽度。

### 5.1 写已可见，确认仍在途

初始 X=0，用一字节读写说明：

| 时间 | 动作 | 结果 |
|---|---|---|
| 80 ns | 目标接纳 W1：X=1 | 尚未更新 RAM |
| 90 ns | 目标接纳 R2：读 X | 依赖 W1 执行 |
| 100 ns | W1 执行提交 | X=1，写确认待返回 |
| 110 ns | R2 执行提交 | 固定读值 1 |
| 115 ns | 源收到 R2 数据 | R2 完成，W1 确认仍可在途 |
| 120 ns | 源收到 W1 确认 | W1 端到端完成 |

在 105 ns 保存时，应保存 X=1、W1 已执行/未确认以及 R2 尚未执行的现场。恢复后不能再执行 W1。

### 5.2 读值固定后不随内存改变

初始 X=0，先接纳 R1，再接纳 W2：X=2。R1 在 100 ns 取值 0；W2 在 110 ns 写入 2；R1 的响应到 130 ns 才到达，也必须仍为 0。

在 120 ns 保存时，仅保存 RAM 中的 2 不够；必须同时保存 R1 响应里的 0。恢复时重新执行读取会产生错误。

### 5.3 不同大小的合法重叠

W64 写 `[0x100, 0x140)`，每字节为 `0xAA`；之后 W8 写 `[0x108, 0x110)`，每字节为 `0xBB`；再之后 R16 读 `[0x100, 0x110)`。

三个请求长度和地址均合法。按目标接纳顺序执行后，R16 应得到 8 字节 `0xAA`，接着 8 字节 `0xBB`。这验证字节范围冲突，而不是仅比较起始地址。

### 5.4 无关请求不需要等较早长请求

目标先接纳 W64 写 `[0x100, 0x140)`，后接纳 R8 读 `[0x200, 0x208)`。二者不冲突，后者允许先执行/返回。若仍被阻塞，应能归因到具体资源或调度政策，而不是虚构同址依赖。

## 6. 响应与源端依赖

- 读响应携带固定的数据；写响应携带该事务的完成确认，不回显写 payload 作为额外业务数据。
- 响应可以按就绪和仲裁结果乱序返回；源端以稳定事务身份匹配。
- 源端不额外强制按发出顺序退休。
- 一个源的多个独立请求可并发；有因果依赖的请求显式等待前项响应完成。
- 未知 ID、重复完成或错误类型属于模型错误，不能靠无条件接受响应掩盖。

Q4 已确认读响应为模型头部加数据、写确认为模型头部；按 bytes/发送域周期计时，整消息交付，每条消息一个接收 credit。头部大小与源端接收容量仍待确认。写无读数据返回不代表写确认零字节、零延迟或不占任何资源。

## 7. 非法访问

以下情况在源侧接纳前验证并明确报错，终止该次运行：

- 不支持的长度，包括零长度；
- 地址未按自身长度对齐；
- 超出 RAM 范围或不合法的地址表示；
- 写 payload 长度与请求长度不符。

组件内部发现非法请求同样终止，并报告组件、事务身份、地址、长度和原因。不生成正常成功响应，不静默丢弃，不进行非法请求的部分写入。

这是 fail-fast 的输入/模型错误政策，不是模拟总线异常。终止运行不自动回滚此前合法事务已执行的写，也不宣称发生了协议级全局 abort/drain。

动态输入可在该请求将被接纳前验证；能静态检查的配置应尽早失败，但首版不要求预加载任意大 trace 才能开始运行。

## 8. Checkpoint 必须保留什么

除一般事件/队列状态外，至少需要：

1. RAM 内容、容量及地址规则身份。
2. 目标接纳顺序和下一顺序号。
3. 每笔尚欠责任的事务处于未执行、已执行待响应或其他明确阶段。
4. 尚未执行的写 payload；已固定的读响应 payload。
5. 冲突依赖所需的地址、长度、操作类型及顺序信息。
6. 已安排的服务就绪/提交/响应动作及有效性。
7. 源 outstanding、已完成身份检查信息和显式输入依赖。

依赖索引可以按权威状态重建，但不能重建出不同的冲突顺序或重复安排动作。写已提交时，快照必须同时体现内存更新和提交身份；不能出现“内存已变，但事务仍标成未执行”的混合切面。

恢复后已执行写不再执行，已采样读不再取值，未交付的响应继续占有明确资源。仅检查最终 RAM 值可能漏掉重复执行同值写，因此测试还要比较执行提交记录及次数。

## 10. 验收案例

以下是待实现测试：

| 编号 | 验收目标 |
|---|---|
| MEM-01 | 七种合法大小均能自然对齐读写，冷启动内容为零 |
| MEM-02 | RAW：早写晚读看到对应执行顺序下的值 |
| MEM-03 | WAR：读响应被阻塞时仍保持写前采样值 |
| MEM-04 | WAW：更晚冲突写最后覆盖，恢复不重复执行 |
| MEM-05 | 重叠读不产生写冲突依赖；非重叠读写允许资源许可下独立完成 |
| MEM-06 | 不同起始地址但区间重叠，按字节范围检测冲突 |
| MEM-07 | 写已提交、ACK 在途时保存；恢复保持写次数和响应身份 |
| MEM-08 | 读已取值、RAM 随后变化时保存；恢复返回原 payload |
| MEM-09 | 多源乱序响应按 ID 匹配，重复/未知响应被发现 |
| MEM-10 | 最后一个合法字节、边界外地址、零长、非对齐、错误 payload 和极大地址均按契约处理 |
| MEM-11 | 请求依赖写 ACK 的路径与无依赖并发路径分别验证，不假设源顺序等于目标顺序 |
| MEM-12 | 冲突等待和响应背压现场 checkpoint 的 A/B/C 轨迹及数据均一致 |

数据参考模型应独立维护字节内存，并检查提交顺序是否满足接纳时的冲突关系；只重放被测模型自行选出的提交序列并核对最终内存，不足以发现错误重排。
