## 1. 目标与非目标

**已确认：**纯 C++ 确定性离散事件内核，首版移除 SystemC 依赖（C36，取代 C3）；SoC 事务级时序性能；独立原型；保留在途状态的 checkpoint；统一可恢复组件契约；受限读写与真实 payload；首版双时钟域与有理数时钟。

C47/C48 进一步确认 ID 不复用；各对象在自身责任终结且最后活动使用者结束后回收，不把所有事件都保留到事务结束。内存可复用但新对象获新 ID，编号分配进度随 checkpoint 保存；位宽与具体接口仍待冻结，见 [09](./09_discrete_event_kernel.md#47-id-不复用与按责任回收)。

C49 确认拥有引用、弱句柄和身份标签分开表达，保活与访问/修改权限分离。C50/C51 进一步确认接纳提交时交接、入队后必要共享、失败仍由原队列持有，以及受控 shared_ptr 实现 OwnerRef；具体共享角色、接口与分配策略尚未冻结。

C52 确认超时检查保活原事务、事务侧弱句柄回指。C53 确认 [七条实施原则](./02_design_contracts.md#0-实施原则与决策边界) 和 [四组最小规范](./05_decisions_and_open_questions.md#4-下一轮讨论入口)：外部语义集中确认，内部无行为变化的细节实施时决定；尚未授权开始编码。

C54–C58 确认可移植相对路径、C++20/CMake、现有 include/src/tests/ut/tools/design_plan 布局与逐模块单测；ID 等采用 std::uint32_t/std::uint64_t 等固定宽度类型，逐字段范围仍待明确。配置先保留独立接口，不先选 CLI 或 JSON，见 [工程约束](./02_design_contracts.md#61-工程布局相对路径与配置边界)。

需要同时证明三类性质：

1. 模型正确：有限容量、仲裁、背压与完成责任符合定义。
2. 恢复正确：新进程恢复后，规定的后续模型可观察轨迹保持一致。
3. 执行高效：在相同语义和输入下，量化宿主耗时、调度与内存成本。

首版不执行 CPU 指令、不启动 OS。建议暂不实现完整一致性协议、详细 DRAM 命令模型、D2D PHY/replay、DVFS、任意局部 reset、并行分布式仿真和图形配置编辑器。Q1–Q10 的未决外部契约按 A–D 分组冻结，不要求所有内部设计在首行代码前全部完成。

不能把确定性等同硬件准确性；没有独立参考前，不承诺“与真实芯片误差小于某百分比”。

## 2. 候选最小系统

```text
请求源 A --+
          +-- 接入队列 -- 共享仲裁/传输资源 -- 有限容量内存目标
请求源 B --+                                  |
          <---------- 有限容量响应路径 --------+

受限连接：许可 -> 传输 -> 接收缓冲 -> 消费 -> credit 返回
```

完整原型已选择两源、单内存目标；请求与响应方向独立带宽，可同时传输，每方向按完整消息串行发送并采用消息级 RR。建议先只启用一个源验证闭环，再加入双源竞争；两个阶段都保留源/互连域与内存域，不直接从 mesh 开始。

最小系统应回答：

- Outstanding 增大到何时不再提高吞吐？
- 接收端已有空槽，发送端为何仍无 credit？
- 请求与响应路径分别在哪里阻塞？
- 增大队列是改善吞吐，还是仅增加排队时延？
- 相同拥塞现场恢复后，仲裁、credit 和完成顺序是否一致？

首版已选择受限读写与真实 payload。已确认 [Q2 事务契约](./06_memory_transaction_contract.md)：单目标、地址 0 起的可配置 RAM（默认 1 MiB）；自然对齐的 1、2、4、8、16、32、64 B 访问；目标执行提交时写入/取值；重叠且至少一写的请求按目标接纳顺序执行；响应允许乱序。非法访问 fail-fast，不引入 cache coherence、原子操作、虚拟地址或详细 DRAM bank/row。

服务计时到期、内存执行提交和源端消费响应分开记录。Q4 已选择启动前冲突门控、有限服务槽和独立启动间隔，每内存边沿最多启动/提交各一笔。启动时不预留响应槽；到期但响应满则继续占服务槽，读不取值、写不执行。响应使用共享总池，整条发送结束才释放槽；每源消费宽度可配置、默认 1。L/II 均为正整数，按实际启动边沿计数；容量及延迟数值仍待冻结，详见 [08](./08_interconnect_and_memory_service.md)。

Q3 已选择 1 ps 网格、有理数周期累计向上量化和事务级 CDC。新到消息/credit/释放槽位不旁路，预定链路结束可接续已有消息。超时追加一次固定源域周期宽限，详见 [07](./07_time_clock_cdc_and_timeout.md)。

## 3. 总体架构

**已确认 C36：纯 C++ 离散事件内核负责时间推进，组件显式管理可恢复状态。**

```text
实验控制 / 配置 / 输入
            |
组件模型：请求源、互连、服务目标、响应路径
            |
组件运行契约：显式状态、事件记录、稳定身份、提交阶段
            |
纯 C++ 离散事件内核：逻辑时间、时钟计算、事件日历、确定性派发

横向：checkpoint、trace、统计、不变量与性能计量
```

内核不实现协程或任意线程挂起，不引入独立前进的第二套时间权威。它仅管理本原型的业务动作与确定性提交语义。C37/C39 已确认单宿主线程、全局可索引最小堆，取消/改期主动移除旧记录；多线程以后按性能证据评估。组件一次处理动作后返回，等待体现在显式状态和到期动作中。

C38 已确认统一周期只服务采样、维护或明确的周期行为，不阻挡精确业务事件。C40/C41 限定 Queued 可取消/改期、Selected 锁定；真改期保持 ID 并更新版本/顺序，无变化无操作。C42 每组件保留最早下一次激活，业务事实独立保存并在处理后重算后续需求。C43 默认周期诊断快照看提交前，checkpoint/完成结算保持提交后。

C44–C46 进一步确定全时钟域共享六阶段：前态观察、到期收集、候选评估、仲裁与提交、结果检查、保存边界。每阶段入口整批 Selected；禁止向本时刻当前/过去阶段新增或改期，不静默加 tick。具体枚举/API 与快照 schema 仍待冻结。

关键业务状态不能只存在于暂停线程的栈、裸指针或捕获闭包中。长操作表示为“当前状态 + 截止时间 + 可恢复事件”。

C++ 标准、工具链、测试和序列化依赖在实施前冻结并验证。首版不依赖 SystemC，也不承诺双后端。内核替换不自动带来加速，必须测量；具体候选设计见 [09](./09_discrete_event_kernel.md)。

### 与已有平台的关系

| 参考 | 借鉴内容 | 不直接移植的能力 |
|---|---|---|
| n_project | 行为/资源/时序/拓扑分离、事务追踪 | 内部协议、完整继承体系及现有模块直接恢复 |
| gem5 | 显式模型状态、事件与统计的契约意识 | CPU/Ruby/Garnet 全部生态或既有 drain 行为 |

## 4. 模块职责

| 模块 | 首版候选责任 | 主要恢复状态 |
|---|---|---|
| 实验控制 | 装配、运行、保存、恢复、结束 | 运行阶段、配置/输入身份 |
| 时间服务 | 1 ps 逻辑时间、双域有理数边沿 | 当前逻辑切点、周期分数、原相位、边沿序号/余数 |
| 动作调度 | 注册、取消、唤醒和确定性派发 | 活跃事件、序号、有效性 |
| 请求源 | 有界 outstanding、背压反馈 | 游标、待发请求、随机流 |
| 事务管理 | 稳定身份、完成与错误责任 | 生命周期、依赖、时间戳 |
| 队列/仲裁 | 有限容量、明确选择和传输 | 队列顺序、仲裁位置、预留 |
| 链路/credit | 双向独立传输、CDC、按消息额度及控制返回 | 整消息进度、同步进度、接收槽位、返回动作 |
| 内存目标 | 启动前冲突门控、读写延迟、启动间隔、有限服务槽 | 内存、payload、接纳顺序、在服务/到期未提交事务、响应缓冲 |
| 超时诊断 | 原 deadline 与一次源域宽限，完成优先 | 原/最终截止点、宽限状态及统计 |
| 观测 | trace、阻塞原因、占用与延迟 | ROI、积分、计数、输出分支 |
| Checkpoint | 保存、验证、装载与恢复协调 | manifest、schema、校验信息 |

这是一张职责表，不要求每行必须成为独立基类或插件。

## 5. 性能路线

按以下顺序推进，不能先承诺比 n_project 快多少：

1. **减少无效工作**：空闲时不轮询；长延迟用完成事件；合并重复唤醒；默认限制文本 trace。
2. **等价优化**：同一合法阶段批处理、紧凑存储、稳定 ID 索引、减少重复查找；对象池在 profiling 支持后引入。
3. **近似或并行**：时间解耦、模型替代、并行分区后续单独设计，不能隐藏在普通性能开关中。

跳过周期必须保留 aging、timeout、周期仲裁等影响。批处理不能突破阶段边界或改变公平性。

Checkpoint 首版建议采用同步完整快照。增量保存、压缩和后台写盘先不承诺；分别测量保存暂停、恢复耗时、大小和额外内存后再决定。

## 6. 里程碑与放行条件

全部为计划，当前均未实施。

| 阶段 | 交付内容 | 放行条件 |
|---|---|---|
| P0 分组冻结与基础模块启动门槛 | A 工程/表示、B 输入/结束、C checkpoint 协议、D 配置/输出；已有内核语义不重开 | A 确认并获明确编码授权后可实施基础模块；B/C/D 最小规范在首个端到端闭环放行前确定 |
| P1 可恢复闭环 | 单源启用、双域有理数时钟、CDC、有限资源/credit、真实读写返回、最小可比 trace | B/C/D 最小规范已确认；跨域与服务中途保存，新进程恢复数据、相位及轨迹一致，具备独立手算与资源检查 |
| P2 资源与竞争 | 双源、队列、仲裁、credit/背压 | 队满与信用耗尽现场可恢复，账本守恒 |
| P3 实验与诊断 | ROI、规范化 trace、统计、首次分歧报告 | 能解释瓶颈并定位恢复差异 |
| P4 性能优化 | profiling、等价优化及性能报告 | 相同语义轨迹一致，实测收益可复核 |
| P5 扩展验收 | 一种新增拓扑或服务模型 | 新组件可恢复，既有双域/有理数/拥塞回归不退化 |

双时钟与有理数相位恢复是首版 P1 验收，不推迟到扩展阶段。单时钟可作为局部单测，但不能替代端到端双域验收；不自动扩展到 DVFS。

架构主干已足以支持基础模块设计，剩余重点是 A–D 四组可执行规范，不再增加无实际用例的新抽象。A 已确认 C++20/CMake、相对路径、目录/单测及固定宽度整数方向，具体环境/测试工具、字段映射与时间输入范围尚未完整冻结；当前仍未授权编码。CLI/JSON 暂缓不阻塞经批准后的模块配置接口与单测，但不替代有效参数或 checkpoint 格式选择。高级统计/性能预算可后续细化，P1 必需的最小观测和恢复检查不可后移。

## 7. 风险与实施入口

| 风险 | 对策 |
|---|---|
| 组件隐式状态不可恢复 | 组件状态清单和恢复测试从 P1 开始 |
| 自建内核过度复杂 | 只实现业务事件、时间与确定性提交；不复制通用进程、信号或协程框架 |
| 稳定顺序被误作硬件仲裁 | 仲裁政策显式建模，排序只保证执行可重复 |
| checkpoint 扰动业务 | 对照无保存、保存继续、新进程恢复三种运行 |
| 性能优化改变语义 | 规范化 trace 与独立参考双重检查 |
| 范围扩张到全系统 | 每个新增机制必须对应问题、状态和验收案例 |

依 C53，基础模块实现前需收敛 A 余项并取得明确编码授权；完整闭环按 B/C/D 最小规范及 P1 验收放行。后续每个模块与 `tests/ut/` 单测同步交付。当前只更新规划与经用户批准的项目指导，不新增源码、CMakeLists.txt 或单测实现。
