## 1. 拓扑与责任

首版完整原型为两个请求源、一个 RAM 目标；开发阶段可以先只启用一个源，仍保留两个时钟域。

```text
                  源/互连域                         内存域
源 A 待发 FIFO --+
                 +-- 请求 RR --> 请求串行链路 --> CDC --> 目标等待队列
源 B 待发 FIFO --+                                     |
                                                  冲突门控
                                                      |
                                                 有限服务槽
                                                      |
源 A 响应接收队列 <-- CDC <-- 响应串行链路 <-- 响应 RR <-- 提交/响应缓冲
源 B 响应接收队列 <---+                       按目标源分组

请求 credit：目标等待槽释放 -> 独立控制延迟/CDC -> 请求侧共享额度
响应 credit：源接收槽释放   -> 独立控制延迟/CDC -> 该源对应响应额度
```

- C21：请求与响应方向拥有独立带宽，可以同时传输。
- 请求发送由源/互连域驱动，响应发送由内存域驱动。
- 每方向一次串行发送一条完整消息，不交错不同消息的字节。
- 不含 mesh 路由、crossbar、多目标地址路由或半双工方向切换。
- 控制通道是有延迟、无共享带宽竞争的抽象，不表示物理实现免费或零延迟。

## 2. 消息大小与链路占用

C25：按字节计时、整消息交付，每条消息消耗一个接收 credit。

令 L 为合法业务数据长度，H(type) 为该类消息的模型头部字节数：

| 消息 | 线侧计费大小 |
|---|---|
| Read request | H(read request) |
| Write request | H(write request) + L |
| Read response | H(read response) + L |
| Write acknowledgement | H(write acknowledgement) |

头部数值及不同类型是否共享一个头部配置尚未冻结；它是模型开销，不是 C++ 对象的 `sizeof`。写 ACK 不因没有数据而免费。

方向带宽 W 的单位为 bytes/发送域周期：

```text
N = ceil(message_bytes / W)
在发送域边沿 k 启动 -> 在边沿 k+N 结束
```

建议 W 和消息大小为正整数，具体输入约束待冻结。尾拍未用满的字节仍占一拍。整个传输途中不允许部分内存写，也不采用逐 beat credit。

**已补充确认 C28：**若下一条消息和所需 credit 在结束边沿前已经可用，可以在 k+N 直接启动下一条；占用区间首尾相接，不人为插入空拍。若当拍才到达消息或返回 credit，则不允许使用。

在有理数时钟下使用 `edge(k+N)` 计算终点，不能用 `N*ceil(period)`。链路结束不等于接收端可见，随后还有传播/CDC。

接收槽按最大合法消息容量建模，最小消息和最大消息各占一个槽；不将“消息 credit 数”误报为“字节 buffer 大小”。

## 3. 消息级轮询仲裁

C22 的规则：

- 请求侧每个源 FIFO，仅队首参与竞争；不越过本源队首。
- 响应侧按目标源逻辑分组，每组最早就绪响应参与竞争。
- 跳过没有消息或没有该接收池 credit 的组。
- 从 RR 指针起循环查找，只有**实际启动发送**才将指针推进到获胜组之后。
- 链路忙、无 credit、只评估了候选但没有发送，都不推进指针。

响应组内次序按执行提交形成的就绪顺序，不强制按原请求顺序；因此读写服务差异仍可产生乱序响应。

这是消息级机会公平，不是字节带宽公平。大小不同的消息轮流获得链路时，大消息占用更多周期；没有 credit 的组也不能获得有界完成时间承诺。

**已确认 C29：**目标待发响应采用共享总池，按源维护逻辑 FIFO；任一源可以使用全部空闲容量，不设置固定的每源份额。RR 初始位置仍待确认。

共享池提高容量利用率，但源 A 长期无接收 credit 时，A 的积压响应可能占满总池，阻塞源 B 请求的执行提交。RR 只能调度可发送者，不能保证缓冲容量隔离。此处“共享总池”不改变各源独立响应接收池的 credit 账本。

## 4. Credit 与容量账本

### 4.1 配额的生命周期

对每个独立接收池，采用下列消息槽账本：

```text
C：发送侧已知且尚未消耗的 credit
F：已获得配额、仍在发送/传播/CDC 中的消息
Q：接收队列中尚未释放的占用
R：接收槽已释放，但 credit 尚在返回路径中

C + F + Q + R = 接收池容量

发送启动        C -> F
整消息可见入队  F -> Q
接收者释放槽位  Q -> R
返回许可可见    R -> C
```

这是配额账本，不是把 Q、F、R 都当成不同物理缓冲占用。入队前已有对应配额，不能先无许可发送、到达再发现队满。

请求目标等待队列是一份共享池，由请求仲裁统一扣减；不能给 A、B 各配置一份完整池容量。响应接收池则按源分别计量。

### 4.2 已确认释放点

C26：

- 请求接收槽在请求启动服务、移出目标等待队列时释放；等待冲突解除时不能提前释放。
- 响应接收槽在源消费响应时释放，不在 CDC 开始或仅入队时释放。
- 释放后的 credit 经控制传输延迟与跨域同步后才变为发送端已知额度。
- 额度可见提交后，下一发送域边沿才允许使用该新额度。

目标等待槽与服务槽是不同资源：请求启动服务时占据服务槽，同时释放等待槽。响应接收 credit 也不是目标本地响应缓冲空间，不能混用。

C50/C51 的成功接纳交接和 shared_ptr 只管理业务责任与宿主数据寿命，不重定义这些槽位。响应发送启动时，发送状态可接管 payload，但共享响应池仍计入正在发送占用，直到 C30 规定的发送结束才释放。之后 CDC 继续保活数据；增加或移动强引用不能重复扣 credit，也不能提前释放槽。交接失败仍保留原队列责任，见 [09 交接约定](./09_discrete_event_kernel.md#410-受控-shared_ptr-与接纳交接)。

控制通道不占数据带宽，但所有返回记录仍须显式保存。R 的总量受接收池容量约束，不能生成重复或无来源的返回。

建议冷启动空队列且发送侧初始 C 等于对应容量，不模拟 credit 训练协议；初始化方案尚未确认。恢复不能重新灌入全额 credit。

### 4.3 源端消费宽度

**已确认 C32：**每源独立配置正整数消费宽度 U，默认 U=1。每个源域边沿按 FIFO 顺序消费至多 `min(U, 边沿前已有响应数)` 条；每条都需匹配事务、记录完成并释放对应接收槽，产生一份返回额度。

两个源互不共享这个消费预算；默认可同拍合计消费两条。消费不强制源请求按发出顺序退休，只遵循响应接收 FIFO。零宽度或负数不是合法配置，不能以 U=0 静默禁用消费。

本拍新入队响应仍不可消费；本拍释放的 outstanding 对新请求接纳的可见性遵守 no-bypass，具体输入接纳接口由 Q5 定义。

## 5. 目标服务与响应背压

### 5.1 启动资格

C23：冲突在启动服务之前处理。

目标选择等待队列中**最早接纳且当前可启动**的请求，条件包括：

1. 所有更早接纳的冲突请求均已执行提交。
2. 边沿前已有空闲服务槽。
3. 启动间隔限制允许本拍发起。

允许跳过被依赖阻塞的请求去服务无关地址，但不能跨过任何更早未提交的冲突关系。读/读不构成冲突，冲突定义见 [Q2](./06_memory_transaction_contract.md#4-冲突与顺序)。

前项本拍才提交时，后项下个内存边沿才能因此启动。响应尚未回源不再保留已提交操作的数据依赖。

### 5.2 服务时间与吞吐

C27：

- 读/写分别配置固定服务周期数 Lr/Lw。
- 服务槽数 K 限制同时在服务及就绪未提交的事务数量。
- 启动间隔 II 控制发起速度。
- 每个内存边沿最多启动一笔，最多提交一笔。
- 提交从“已到期且有响应保存空间”的事务中选择最早接纳者。
- 启动与提交可同拍，但不能使用该拍刚释放的服务槽。

**已确认 C34/C35：**

- Lr/Lw 为正整数内存周期；边沿 k 启动的请求在 `memory_edge(k+L)` 最早提交，不支持 L=0。到期后被响应空间阻塞，只等待提交资格，不重算 L。
- II 为正整数，按上一次实际启动边沿计数。上次在 k 启动，则下一次不能早于 k+II；II=1 允许每拍启动一笔。
- 这不是固定周期发射窗口。例如 II=3，上次在 10 启动，13 因无资源未启动，14 具备资格即可启动；成功后下一次最早是 17。失败尝试不重置计数。

默认 Lr/Lw/II 数值仍未确定；冷启动第一次允许发起的边沿仍属于初始化决策。

等待队列可能有请求、服务槽也空闲，但仍受冲突或 II 阻塞。此模型不是 DRAM bank/row/refresh 模型。

### 5.3 用户选择：响应满时占槽等，不预留响应槽

C24 明确采用以下行为：

```text
目标等待
 -> 启动并占服务槽（不预留响应槽）
 -> 服务计时到期
 -> 有响应空间：执行提交、生成响应、释放服务槽
 -> 无响应空间：保持 ready-but-uncommitted，继续占服务槽
```

在 ready-but-uncommitted 状态：

- 写尚未更新 RAM，读尚未采样数据。
- 不重新启动服务计时；每个后续内存边沿按条件竞争提交。
- 更年轻冲突请求仍不得启动。
- 不把结果写入无容量限制的临时容器来绕过响应缓冲。

提交时原子形成“内存操作结果 + 已执行身份 + 有限缓冲中的响应责任”。即使另一笔响应本拍释放空间，也必须下一内存边沿才能使用该新空间。

**已确认 C30：**本地响应槽从执行提交开始持有，直至整条响应发送结束才释放。开始发送可以将响应从逻辑待发 FIFO 标记为当前发送者，但不能提前归还共享池槽；不额外增加一消息发送暂存容量。

令共享响应池容量为 B，本地账本为：

```text
free_slots + queued_responses + serializing_response = B
queued_responses = 各源待发逻辑 FIFO 的长度之和
serializing_response 为 0 或 1
```

提交检查的是边沿前共享总池的空槽。本拍发送结束释放的槽，下个内存边沿才能用于新提交。若已有另一条待发响应及远端 credit，则链路仍可在本拍无缝接续：它使用自己已经持有的槽，不需要借用刚释放槽。

本地响应槽释放不等于源已收到响应。发送结束后，传播/CDC 中的消息仍占远端接收池账本中的 F；必要 payload 与交付责任必须保留到后续阶段，不能因归还本地槽而删除。两份账本保护不同资源，不能互相代替。

## 6. 双域手算时间线

### 6.1 教学条件，不是默认值

此例只证明计数关系，使用整数周期以便手算；有理数频率另见 [07](./07_time_clock_cdc_and_timeout.md#2-有理数时钟)。

- 源/互连域 1 GHz：边沿间隔 1000 ps；内存域 800 MHz：间隔 1250 ps；两者零相位。
- 一笔 8 B 读在 t=0 被源接纳，已排队，t=1000 开始发送；无其他业务。
- 所有头部 16 B，两方向均为 16 B/发送域周期。
- 两向数据传播延迟和 credit 控制延迟各取 500 ps，随后再 CDC。
- CDC 采用已确认 C31 计数，教学取 S=2；源消费宽度采用默认 U=1。
- 读服务 Lr=2；队列、服务槽和响应空间均充足，初始 credit 充足。
- 本地响应槽按已确认 C30，在发送结束释放。

除明确已确认的行为和 U=1 默认值外，其余数值只作为本例假设，不能直接复制成项目默认配置。

### 6.2 请求、服务、响应

| 时间 ps | 动作 | 判断依据 |
|---|---|---|
| 0 | 源接纳 8 B 读 | 教学输入起点 |
| 1000 | 请求开始发送，扣一个目标等待池 credit | Read request 仅 16 B 头部 |
| 2000 | 请求发送结束 | 占 1 个源域周期 |
| 2500 | 数据传播完成 | 恰好命中内存边沿，仍不能本边沿采样 |
| 3750 | CDC 第 1 级 | 严格更晚的内存边沿 |
| 5000 | CDC 第 2 级，目标接纳入队 | F -> Q，本边沿不能启动该请求 |
| 6250 | 启动内存服务，释放等待槽 | 可用状态来自上一边沿；Q -> R |
| 8750 | 服务到期并提交，固定 8 B 读值 | 两个内存周期；边沿前已有响应空间 |
| 10000 | 响应开始发送 | 提交当拍生成的新响应不能当拍发送 |
| 12500 | 响应发送结束 | 24 B 消息占 2 个内存周期 |
| 13000 | 数据传播完成 | 恰逢源域边沿，不能当拍采样 |
| 14000 | 响应 CDC 第 1 级 | 严格更晚源域边沿 |
| 15000 | 响应 CDC 第 2 级，入源接收队列 | 入队不等于完成 |
| 16000 | 源消费、匹配响应，端到端完成 | no-bypass；释放响应接收槽 |

从源接纳到完成为 16000 ps，从首次发送到完成为 15000 ps；二者不是同一 latency 指标。

### 6.3 Credit 与宽限期

- 请求等待槽在 6250 释放，控制传播到 6750；源域第 1/2 同步边沿为 7000/8000；返回 credit 最早在 9000 可用于发送。
- 响应接收槽在 16000 释放，控制传播到 16500；内存域第 1/2 同步边沿为 17500/18750；返回 credit 最早在 20000 可用于响应发送。
- 若本例原 D=14000、G=2，严格更晚的两个源域边沿为 15000、16000；16000 正常完成优先，因此记录宽限内完成，不报超时。D 的数值不代表已选择 timeout 起点与默认时长。

建议保存切点包括请求 CDC 中、服务未到期、读值已固定但响应未发、响应在途和宽限期内。满响应缓冲的 ready-but-uncommitted 切点另用竞争负载覆盖。

## 7. 可恢复状态与性能解释

除 RAM 与事务身份外，必须覆盖：

- 每源 FIFO、响应逻辑分组顺序、两方向 RR 指针、实际发送序号及下一序号。
- 当前整消息、起始/结束边沿、传输占用；不必逐 beat 建事件，但须能唯一恢复进度。
- 每个接收池的 C/F/Q/R、CDC 消息和返回记录。
- 目标接纳序号、等待/服务集合、L 到期边沿、上一次实际启动或等价的 II 下一可启动边沿。
- 已到期未提交状态、未执行写 payload、已固定读 payload。
- 共享响应池的空槽、排队和正在发送占用；发送中途恢复不能提前释放或重复分配槽。
- 每源 U 配置身份及响应接收顺序；恢复不修改消费宽度。

统计建议分别记录等待冲突、无服务槽、II 限制、响应满、无 credit、链路忙和 CDC 延迟；多个原因同时成立时不要简单相加冒充总等待时间。

可用于解释但不能替代实测的上界：

- 每方向链路受 `ceil(message_bytes/W)` 和发送域频率限制。
- 无其他阻塞时服务启动受 `II`、每边沿启动宽度和 K 共同限制。
- 每内存边沿最多提交一笔；响应满会使实际服务槽占用超过固定 L。
- Credit 往返包含等待/消费、控制传播、CDC 与 no-bypass；延迟长且池小可能限制吞吐。
- RR 的消息公平不意味着 payload 吞吐相同。

分析应同时报告 payload bytes 与包含头部的线侧 bytes，不能把名义 W 直接当应用数据吞吐。
